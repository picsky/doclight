# 05 · 事件流产品化：Agent 的「镜子」

> **核心问题**：Agent 的工作过程（思考、工具调用、出错）怎么变成产品体验（用户看到的）与合规证据（你留存的）？这是「做产品」与「调 API」的分界线——API 只给你结果，事件流给你过程。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：订阅 API 见 `../sdk-docs/03-快速上手-TypeScript.md` §6 / `../sdk-docs/04-接口参考-Python.md` §6；事件词汇表见 `../deepseek-harness-解析.md` §2.1；原理见课程第 06 章。

---

## 1. dsh 给了什么（过程数据）

| 事件 | 产品价值 |
|---|---|
| `assistant/chunk` | **流式打字机效果**——逐 token 推给前端 |
| `tool/call` + `tool/result` | **工具卡片**——用户看到「它在查什么、结果如何」；审计原料 |
| `turn/start/end`（reason） | **进度与结局**——completed/max-tokens/error/aborted… |
| `agent/inbox/spliced` | 入队回执（消息确实被接收） |
| `subagent.started/finished` | 多 Agent 可视化（子任务树） |
| `user/message`（含注入） | 完整上下文重建（合规：模型看到了什么） |
| `request/header` | 每次请求的配置与组装快照 |

**关键认知**：dsh 的事件流是**构造性的**——它不只是「监控日志」，而是「模型输入与输出、系统决策的完整账本」。你的产品可以零埋点获得完整 Trace。

## 2. 你要做什么：三类产品化消费

### 2.1 体验类：把过程变成界面

| 事件 | 界面形态 |
|---|---|
| assistant/chunk | 流式文本（打字机） |
| tool/call | 「正在调用 X 工具…」+ 参数摘要（可展开） |
| tool/result | 结果卡片：成功/失败徽标 + 提炼内容 |
| turn/end | 步骤完成标记、原因徽标（⚠ max-tokens / ❌ error） |
| subagent.* | 子任务树/嵌套进度 |

**设计原则**：展示「提炼后的过程」，不是「事件流原文」。产品 UI = 事件流的一个**投影**——和 dsh 自己的 TUI 卡片（presentCall/presentResult）同一哲学。

### 2.2 合规类：审计证据落库

```python
def audit_to_db(notification):
    if notification.method != "session.event":
        return
    ev = notification.payload["event"]
    row = {
        "session_id": notification.payload["sessionId"],
        "seq": ev["seq"],
        "ts": ev["time"],
        "type": ev["type"],
        "data": ev["data"],          # 原始载荷（tool/call 的参数是模型原样 JSON）
    }
    audit_table.insert(row)          # 你的审计存储（不可变语义：只插不删）

# 常驻审计进程：订阅 → 落库 → 按需查询
sub = harness.client.subscribe_session_notifications(sid)
while True:
    audit_to_db(sub.next())
```

**审计必留字段**：tool/call 的 `arguments`（模型原始输出）、tool/result 的 `error`、turn/end 的 `reason.kind`、user/message 的 `source`（区分用户输入与注入）。**这些就是「模型看到了什么、做了什么、结果如何」的完整证据链。**

### 2.3 监控类：运营指标

| 指标 | 数据来源（事件流） | 回答的问题 |
|---|---|---|
| 成功率 | turn/end.reason 分布 | 产品健康吗？ |
| 工具错误率 | tool/result.error 计数 | 工具设计问题？ |
| 平均/最大 token | assistant/message.usage | 成本趋势？ |
| 步数分布 | step/end 计数 | 效率？（5 步 vs 20 步完成同一任务） |
| 人工介入率 | 你的审批记录 + turn/end.aborted | 自动化程度？ |
| 循环信号 | 同工具重复调用频率 | Agent 卡壳？ |

**落地**：消费事件流 → 聚合 → 看板。注意课程第 06 章「人类注意力是隐藏成本中心」——**每 PR/每任务人工审查分钟数**这类指标要单独设计采集。

## 3. 怎么做：事件消费架构

```
你的产品后端
  ├── 订阅层：session.event 订阅（按 session 过滤）
  ├── 处理层：
  │     ├── 体验投影 → WebSocket/SSE 推前端
  │     ├── 审计投影 → 审计库（只插不删）
  │     └── 指标投影 → 聚合器 → 看板
  └── 查询层：session.jsonl 回放 / 事件查询（按 session+seq）
```

**两种消费模式**：

| 模式 | 用法 | 适用 |
|---|---|---|
| **实时订阅** | `on_notification` 回调 / subscribe | 流式 UI、实时监控 |
| **事后回放** | 读 `session_root` 下 JSONL | 审计查询、事故复盘、评估集建设 |

## 4. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 把事件流当「结果」 | final_response 语义混淆（区间结果非因果） | 理解 owned-run 区间（`../sdk-docs/01-架构与工作原理.md` §4） |
| 事件全量入前端 | 带宽、隐私、实现复杂度 | 后端投影，前端只收展示用视图 |
| 审计只存结果不存过程 | 出事故无法复盘 | tool/call 原始参数必留 |
| 忽略 chunk 流 | 体验回到「等完整回复」 | 流式消费（打字机是 Agent 产品的标配体验） |
| 指标只看成功率 | 隐藏质量问题（虚假成功） | 分层：reason 分布 + 工具错误 + 步数 + 人工介入 |
| 事件处理阻塞 | 拖慢订阅消费（背压） | 异步处理（落库/投影与主流程解耦） |
| 隐私不设防 | 敏感过程数据泄露 | 事件流过滤/脱敏层（产品侧） |
