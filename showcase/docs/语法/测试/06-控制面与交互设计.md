# 06 · 控制面与交互设计：用户与 Agent 的「对话界面」

> **核心问题**：Agent 不是黑盒自动化——产品需要在关键节点让用户介入（打断、转向、审批、升级）。控制面设计决定产品是「人机协作」还是「失控自动化」。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：审批链机制见 `../deepseek-harness-解析.md` §3.1；交互 API 见 `../sdk-docs/04-接口参考-Python.md`；原理见课程第 07 章。

---

## 1. dsh 给了什么（交互基础设施）

| 机制 | 作用 | SDK 面可达？ |
|---|---|---|
| `agent.steer()` | 回合运行中注入转向（下一步生效） | ❌（协议无此方法）——**L3 控制面** |
| `agent.inject()` | 注入上下文（不进回合） | ❌ |
| `agent.cancel()` | 取消活动（区分 keepInbox） | ⚠️ 协议无 prompt-cancel——放弃=关 runtime |
| **approval 链** | 工具级审批（ask → allowed-once/拒绝） | ✅（工具配置层） |
| **commands** | 斜杠命令（绕过模型直执行） | ❌（产品侧实现） |
| **user-questions** | 工具/权限插件的「问人」界面 | ✅（工具配置层） |
| **jobs/schedule/goal** | 后台任务/定时/同会话目标 | ❌（配置或 L3） |
| **turn-stopping 钩子** | 回合停止前拦截（可续步） | ❌（插件层） |

**关键认知**：交互基础设施 dsh 有，但**大部分在 SDK 协议面之外**（协议只有 3 个方法）。产品级交互设计 = 你的产品逻辑 + 按需引入 L3 控制面（Node 服务）或利用工具层的审批/问人机制。

## 2. 你要做什么：交互矩阵设计

对每个「用户与 Agent 的接触点」设计行为：

| 接触点 | 场景 | 产品行为 | dsh 机制 |
|---|---|---|---|
| **打断** | 用户发现方向错了 | 停止当前回合 → 重定向 | 关闭 runtime（SDK 面）或 L3 `cancel()` |
| **转向** | 任务进行中调整要求 | 注入转向，下一步生效 | L3 `steer()`；SDK 面：新 session 续接 |
| **追问** | 信息不足 | 阻塞式提问（选择/文本） | 工具层 `ask` / user-questions |
| **审批** | 危险操作 | 展示意图 → 同意/拒绝/改参数 | approval 链（`allowed-once` 等） |
| **升级** | 重试耗尽/低置信 | 人工队列 + 上下文打包 | 你的编排逻辑 + 事件流 |
| **确认** | 对外交付 | 展示产物 → 确认发布 | 你的流程设计 |
| **反馈** | 结果不对 | 用户标记 → 回流改进 | 你的反馈接口 + 迭代闭环（07 篇） |

## 3. 怎么做：两类交互的实现路径

### 路径 A：SDK 面（不写 TS，覆盖 80% 交互）

利用**工具层机制**实现人机协作——不需要控制面：

```python
# 审批：危险工具要求确认（工具配置层）
# cordis.yml 中该工具的审批策略 → 工具被调用时进入 ask
# 产品侧：监听事件流，工具被 ask 时弹审批 UI，结果回传 approval 服务

# 追问：让 Agent 遇到信息不足时调用「问用户」工具
# 自定义工具 ask_user(question, options) → 产品 UI 展示 → 结果作为工具结果返回
```

交互流程（SDK 面完整闭环）：
```
用户发起任务 → Agent 执行 → 遇到危险操作 → 工具 ask → 产品 UI 弹窗
  → 用户同意 → 工具继续 → 完成 → 交付确认 → 用户反馈 → 迭代闭环
```

### 路径 B：L3 控制面（交互密集产品才需要）

交互是产品核心（工作台形态、实时协作）时引入 Node 控制面：

```ts
// Node 控制面（dsh 内核）——你的产品编排服务
agent.steer(message)                  // 用户转向 → 下一步生效
agent.inject(context)                 // 注入上下文（文件变化、外部事件）
await agent.cancel({ kind: 'user' })  // 打断当前回合
ctx.goals.set(agent, objective)       // 同会话目标
ctx.jobs.start(...)                   // 后台任务
// 通过你自己的 API（Typert RPC / HTTP）暴露给 Python 业务侧
```

> 决策依据见 `../product-knowledge/03-流程编排层.md` §4 与前面「语言边界」讨论：交互密集 + 需要引擎级控制 → Node 控制面；常规交互 → SDK 面足够。

## 4. 触发方式设计（谁启动 Agent）

| 触发 | 实现 | 典型场景 |
|---|---|---|
| **用户手动** | 产品 UI → run() | 对话、按需任务 |
| **定时** | schedule 插件（配置）或你的 cron → run() | 每日报告、周期巡检 |
| **事件驱动** | 你的后端事件 → run() | 新数据到达、CI 失败、工单创建 |
| **批量** | 你的编排循环（多 session 排队） | 批量审查、批处理 |

**注意**：SDK 面的触发 = 你的代码调 run()；schedule/jobs 是 dsh 内部能力，协议面不可直接调（`../sdk-docs/06-协议参考.md` §6）。

## 5. 人工兜底：产品可靠性的最后防线

```
每类任务的兜底路径设计：
  正常路径：Agent 完成 → 交付
  重试路径：失败 ≤2 次（带修复指令）
  降级路径：部分结果 + 明确标注「未完成」
  升级路径：人工队列（上下文打包：任务描述 + 事件流摘要 + 已尝试）
  紧急路径：人工可直接接管（停止 agent + 手动处理）
```

**打包上下文模板**（升级时给人看的）：
```
任务：xxx
目标会话：sid
已尝试：步骤1（成功）→ 步骤2（重试2次失败：工具返回错误 XXX）
关键事件：turn/end reason=error；tool/result error={...}
原始输入：<任务原文>
```

## 6. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 无打断设计 | 用户只能干等或关页面 | 至少提供「停止 + 重来」路径（SDK 面=关 runtime+新会话） |
| 审批过多 | 用户体验崩（每步都弹窗） | 审批只给危险/不可逆操作；常规操作静默 |
| 审批过少 | 事故 | 破坏性操作必审（课程 07 章） |
| 无升级路径 | 失败=任务死亡，用户求助无门 | 兜底三连：重试→降级→升级 |
| 交互密集却用 SDK 面硬凑 | 体验差、实现别扭 | 评估是否引入 L3 控制面 |
| 反馈无回流 | 同一个错反复犯 | 反馈接口 → 评估集 → 规则回流（07 篇闭环） |
| 上下文打包不全 | 人工接手要重读整个会话 | 升级时自动打包结构化上下文 |
