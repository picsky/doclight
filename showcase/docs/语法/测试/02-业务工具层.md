# 02 · 业务工具层：Agent 的「手」

> **核心问题**：你的产品世界里，Agent 能碰什么、怎么碰得可靠？工具是业务能力与模型之间的「汇率」——课程第 03 章 6.7%→68.3% 的实验说明汇率差 10 倍。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：插件开发教程 `../sdk-docs/07-定制化开发.md` §4；原理见课程第 03 章；dsh 工具管道见 `../deepseek-harness-解析.md` §2.3/§3.2。

## 1. dsh 给了什么（工具基础设施）

| 机制 | 位置 | 作用 |
|---|---|---|
| tools 管道 | `ctx.tools` | 注册表 + 五段守卫管道（pre-execute → 守卫 → execute → post-execute → result） |
| `defineTool` DSL | `dsh-tools` | 类型化 schema（参数/输出推断）、规范输出契约、presentCall/presentResult |
| 内置工具 | bash/fs/web/lsp/terminal/skills… | 通用能力开箱即用，**业务工具自己写** |
| 能力接缝 | capability seam | 换 provider 不换 schema（本地↔远程沙箱） |
| 权限 | `restrict`/`approval`/ToolGuard | 工具级白名单/审批/单调守卫 |
| 超时/取消 | timeout-policy + signal | 每个工具有超时预算，协作式取消 |

**关键认知**：管道、schema 校验、错误结构化、审批——dsh 全给了。你的工作是**设计工具**（语义、边界、错误消息），不是实现管道。

## 2. 你要做什么：工具产品化五步

### 第 1 步：能力盘点（业务操作清单）

把产品的所有操作列成表——这是工具集的原材料：

| 业务操作 | 读/写/执行 | 频率 | 危险度 | 现有实现（API/CLI/库） | 需要 Agent 用？ |
|---|---|---|---|---|---|
| 查合同条款 | 读 | 高 | 低 | 内部 API | ✅ |
| 生成审查报告 | 写 | 高 | 中 | Python 引擎 | ✅ |
| 修改生产配置 | 写 | 低 | **高** | 管理台 | ❌（人工） |
| … | | | | | |

**决策规则**：Agent 不需要的操作不包装（攻击面最小化——课程第 07 章「工具=能力=攻击面」）；危险操作要么不暴露，要么走审批。

### 第 2 步：任务级动作设计（不是 API 包装）

课程第 03 章的核心：**一个工具 = 一个任务级动作，不是一组 API 端点**。

```
❌ API 包装（模型要自己编排多步）：
  list_invoices / get_invoice / update_invoice_status / notify_customer

✅ 任务级动作（模型一步完成业务语义）：
  resolve_invoice_dispute(invoice_id, resolution)   # 内部完成查单+改状态+通知
  check_compliance(contract_text)                   # 内部完成拆条款+逐条核对
```

判断标准：**模型「想做成一件事」时，是否只需要调一个工具**？需要调 3 个的，合并。

### 第 3 步：schema 设计（五原则，课程 03 章 §3.1）

1. **命名即提示**：`resolve_invoice_dispute` 优于 `handle`；命名空间区分重叠域
2. **参数语义化**：3 个明确参数优于 1 个万能字符串；`user_id` 优于 `user`（歧义）
3. **枚举收窄**：`status: {enum: [...]}` 优于自由字符串——枚举即确定性
4. **默认值防呆**：模型什么都不传时行为也安全、token 也省
5. **description 写给模型看**：隐含上下文（何时用/何时不用/术语/关系）全写出来——**description 是 prompt 的延伸，改它要走评估**

### 第 4 步：错误消息即修复指令

```
❌ Error: EVALID
❌ {"error": "invalid parameter", "code": 400}
✅ {"error_code": "INVOICE_NOT_FOUND",
    "message": "发票 INV-2026-014 不存在或已归档。",
    "suggestion": "先调用 list_invoices(status=...) 确认发票号与状态——可能是拼写错误或已归档。归档发票用 resolve_archived()。",
    "retry_hint": "re_query_then_retry"}
```

**每条错误消息 = 错误码（程序分支）+ 发生了什么（模型理解）+ 下一步怎么做（模型执行）**。反面：静默成功（`{"ok": true}` 但什么都没改）比报错更糟——模型会在错误状态假设上盖楼。

### 第 5 步：权限边界与审批设计

| 工具类别 | 示例 | 权限策略 |
|---|---|---|
| 只读 | 查询、检索、读取 | 默认放行（restrict 白名单内） |
| 工作区写 | 生成文件、修改草稿 | 放行，结果可 diff/回滚（git 兜底） |
| 外部写 | 发消息、改线上状态 | **审批**（`ask` → approval 链） |
| 破坏性 | 删除、覆盖、外发 | 审批 + 独立工具名（`delete_x` 不与 `write_x` 混用） |

dsh 实现：`ctx.tools.restrict({allow/deny})` 按 agent 过滤 + `PreToolDecision.ask` 走审批服务 + ToolGuard 单调守卫（只能拒绝不能放行——安全边界不可被稀释）。

## 3. 怎么做：从 CLI 到精致工具的两步走

**第一步（跑起来）**：业务逻辑保持你现有的实现（Python 脚本/API），用 bash 工具或薄桥接调用：

```yaml
# cordis.yml —— 先让 agent 能调你的引擎
- id: clause-engine
  name: '@deepseek-ai/dsh-tool-bash'   # 或自建薄插件：执行 python my_engine.py <args>
  config:
    description: "调用条款检查引擎。用法：python /srv/engine/check.py --text <path>"
```

**第二步（精致化）**：业务稳定后，写真正的工具插件（`defineTool`）：
- 结构化 schema（枚举/必填/约束）——错误在调用前暴露而非运行时
- 规范输出（canonical JSON + 提炼后的 content）——不转储原始输出
- 错误码闭集 + 修复指令
- `timeoutMs`、`isConcurrencySafe`、`presentCall/presentResult`（UI 卡片）

> 插件开发完整教程见 `../sdk-docs/07-定制化开发.md` §4（capability seam 三件套 + 打包/源码运行时的路径选择）。

## 4. 工具评估：让工具集持续变好

课程第 03 章 §3.8 的循环照抄：

- **参数正确率**：调对了工具、参数填对了吗？大量无效参数 → description 不清或约束不够
- **工具选择准确率**：该调 A 调了 B？→ 命名边界模糊或功能重叠
- **方法**：真实任务评估集 → 收集 trace → 分析错误模式 → 修 description/schema → 保留集验证
- **纪律**：description 的一词之差就是行为差异——**没有评估兜底的 description 修改等于闭眼调参**

## 5. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 包装 API 端点而非任务 | 模型多步编排，错误成倍 | 任务级动作合并 |
| 万能字符串参数 | schema 校验失效，运行时才错 | 语义化参数 + 枚举 |
| description 敷衍 | 模型猜用法、误用工具 | 写给模型看：隐含上下文全写 |
| 错误消息无修复指令 | 模型盲目重试烧 token | 三件套：码+发生了什么+下一步 |
| 静默成功 | 状态假设错误，10 步后坍塌 | 写操作返回「改了什么」的证据 |
| 工具过多 | token 瘫痪、选择准确率下降 | restrict 白名单 + 按任务阶段筛选 |
| 危险操作无审批 | 注入攻击放大 | 破坏性 = 独立工具 + ask 审批 |
| 工具集不评估 | 凭感觉调 description | 参数/选择准确率两层指标闭环 |
