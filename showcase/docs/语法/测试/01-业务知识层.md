# 01 · 业务知识层：Agent 的「脑子」

> **核心问题**：同一套 dsh，你的产品凭什么比别家的好？第一答案就是知识——Agent 看到什么，决定了它会做什么。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：接口细节见 `../sdk-docs/07-定制化开发.md`；原理见课程第 01/02 章；dsh 机制见 `../deepseek-harness-解析.md` §2.4。

---

## 1. dsh 给了什么（知识注入的机制）

| 机制 | 位置 | 作用 |
|---|---|---|
| **persona / prompt section** | `agent-spine` 配置、system-prompt 分节注册 | 每个请求恒定在场的「行为契约」 |
| **动态上下文注入** | system-prompt 的 `context` 机制 → `user/message` 快照 | AGENTS.md、时间、catalog 等按需注入，**且注入内容进日志**（可审计） |
| **skills 目录** | `dsh-tool-skill`：目录只给 name+description，正文按需加载 | 「给地图，不给百科全书」的机制化 |
| **request/header 快照** | 每次请求的信封（system+tools）落日志 | 模型看到了什么，永远可重建 |
| **preset 组合** | cordis.yml 按 agent 组合能力 | 不同产品场景 = 不同知识面 |

**关键认知**：dsh 给的是「注入管道」，**管道里流什么 = 你的全部工作**。知识质量 = 产品智商的下限与上限。

## 2. 你要做什么：三层知识设计

### 2.1 第一层：产品 AGENTS.md（常驻知识）

设计原则（dsh 仓库自己的 AGENTS.md 就是范本，约 150 行）：

```
# AGENTS.md（你的产品版）
## 本项目是什么（3 行）          —— 定位 + 技术栈 + 当前阶段
## 必须遵守（10 行）             —— 仅有的全局硬约束（违反即返工的那种）
## 去哪里找什么                  —— 指针：业务规则 → docs/…；用户偏好 → …
## 工作方式（5 行）              —— 先读索引再动手；日志写哪；什么需要确认
```

硬规则：
- **≤100–150 行**，只放「每次会话都需要」的
- **每一行对应一次真实失败**（Hashimoto 原则：错误驱动，不写「可能有用」的规则）
- 详细知识进 `docs/` 分层文档，AGENTS.md 只做**目录**

### 2.2 第二层：分层知识库（按需加载）

| 知识类型 | 存放 | 加载时机 | 常驻？ |
|---|---|---|---|
| 全局硬约束（≤10 条） | 产品 AGENTS.md | 每次会话 | ✅ |
| 业务规则（详细版） | `docs/rules/` | 涉及该领域时 | ❌ |
| 领域术语/规范 | `docs/domain/` | 任务相关时 | ❌ |
| 产品架构/数据模型 | `docs/architecture/` | 改代码/查数据时 | ❌ |
| 用户档案（产品级长期记忆） | 你的数据库 → 注入 | 会话开始时 | 摘要 ✅ |
| 历史结论/决策 | 归档 | 争议时回查 | ❌ |

**判断标准一句话**：只有「每个动作都需要」的信息才配常驻（课程第 02 章的加载时机决策表直接套用）。

### 2.3 第三层：persona（行为而非人设）

dsh 的 `agent-spine.config.persona` 就是产品人格。课程第 01 章的教训直接适用：

- ✅ 写行为：「报告问题时先给结论再给证据」「不确定时标注 confidence: low」
- ❌ 写人设：「你是拥有 20 年经验的资深法律顾问」——人设对行为的约束力弱且不稳定
- persona 与 AGENTS.md 的边界：**persona 回答「怎么工作」，AGENTS.md 回答「这个项目/领域的事实」**

## 3. 怎么做：知识盘点与入库流程

```
第 1 步 知识盘点（一次半天）
   - 列出产品域的所有事实类知识：规则/术语/数据模型/流程/边界
   - 每条标注：谁消费（模型/工具/用户）、变化频率、敏感度
第 2 步 分层归类
   - 常驻（AGENTS.md/persona）| 按需（docs/）| 永不（不进上下文）
第 3 步 写成 Agent 可消费的形态
   - 命令优先、代码示例优于文字（GitHub 2500+ 仓库分析）
   - 单行、grep 友好（错误信息、规则条目）
第 4 步 接注入管道
   - cordis.yml 的 agent-spine persona 字段 / 自建 context 插件
第 5 步 维护循环
   - 每次 Agent 犯错 → 检查是否缺知识 → 补一条（错误日志驱动）
   - 知识过期 → 定期复审（新鲜度标记）
```

**可用模板**：知识盘点表

| 知识条目 | 类型(规则/术语/事实) | 谁消费 | 变化频率 | 敏感度 | 去向(常驻/按需/永不) | 来源(哪次失败) |
|---|---|---|---|---|---|---|
| 付款条款必须含违约金 | 规则 | 模型 | 低 | 中 | 常驻 AGENTS.md | 漏检事故 |
| … | | | | | | |

## 4. 长期记忆产品化（跨会话，产品级）

会话内记忆（session 日志）dsh 管；**跨会话的产品级记忆是你的设计**：

| 记忆类型 | 例子 | 载体 | 注入方式 |
|---|---|---|---|
| 用户偏好 | 「这个客户用简体中文报告」 | 你的数据库 | 会话开始时注入（`agent.inject` / 首条 user/message） |
| 历史结论 | 「上次审查发现 X 模块有历史债务」 | 你的业务表 | 相关任务时按需注入 |
| 产品级规则更新 | 新合规要求 | docs/ + AGENTS.md | 版本化，下次会话生效 |

**三条纪律**：
1. 记忆 = 显式读写（你的代码决定何时注入），不是黑盒自动沉淀
2. 可 diff、可审计（注入的内容进 session 日志——dsh 已保证）
3. 会腐烂：用户偏好会变、结论会过时——带时间戳与来源，定期复审

## 5. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 把所有知识塞进 persona | 指令量↑ 单条遵循率↓（课程 01 章反比律） | persona 只放行为；事实进 AGENTS.md/docs |
| AGENTS.md 写成百科全书 | 上下文污染 + 关键指令被淹没 | ≤150 行目录 + 按需加载 |
| 知识存在「人脑/聊天记录」里 | 对 Agent = 不存在（课程 02 章） | 全部入库，仓库即事实来源 |
| 写人设不写行为 | 行为不可控 | persona 翻译成具体行为规则 |
| 知识过期不清理 | 旧规则误导新任务 | 新鲜度标记 + 定期复审 + 删除机制 |
| 规则没有失败来源 | 「可能有用」的噪音规则 | 每条规则对应一次真实失败（错误日志驱动） |
