# 07 · 评估与迭代闭环：产品怎么持续变好

> **核心问题**：同一套 dsh，你和竞品的差距最终落在哪里？——迭代速度。评估不是上线前的验收环节，是产品的**日常开发循环**。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：原理见课程第 06 章（评估分类学/Trace 驱动迭代）；统计层（CI/bootstrap/保留集）见课程第 09 章；事件消费见 `../product-knowledge/05-事件流产品化.md`。

---

## 1. dsh 给了什么（评估基础设施）

| 资产 | 用途 |
|---|---|
| **事件流 = 完整 Trace** | 每次运行的可观测证据——不用额外埋点 |
| **session.jsonl 回放** | 事故复盘、评估集建设原料 |
| **finish_reason** | 自动化质量信号（completed/max-tokens/error…） |
| **持久会话** | 同一任务可重跑对比（同 session_id + 同输入） |
| **审计数据** | 工具调用、注入内容全留痕——评估特征可提取 |

**关键认知**：dsh 把「数据」给全了；你的工作是**建立闭环**——把数据变成改进，把改进变成验证。

## 2. 你要做什么：四件套评估基础设施

### 2.1 产品评估集（核心资产）

从真实失败出发（课程第 06 章方法），三类齐备：

| 类别 | 来源 | 职责 | 占比参考 |
|---|---|---|---|
| **easy（基本盘）** | 日常高频任务 | 防退化——改坏了立刻可见 | ~40% |
| **edge（边界）** | 能力边缘的复杂任务 | 测改进——优化在这里出分 | ~40% |
| **adversarial（对抗）** | 错误日志里的已知失败 | 防复发——每修一类错误加一道闸 | ~20% |

**建设路径**（最小可行，10–30 条就能跑信号）：
```
1. 建立错误日志（从第一天）：日期/场景/错误表现/环境缺了什么
2. 每类新错误 → 转化一条评估用例（复现输入 + 期望行为）
3. 防污染：评估任务不进 AGENTS.md/任何注入文档；对抗样本定期轮换
4. 保留集：≥10 条平时不碰，发布时跑一次（防过拟合，课程 09 章）
```

### 2.2 自动化评分（grader）

- **确定性检查优先**（能用代码判的绝不用 judge 判）：
  - 文件/输出断言（`file_contains`、`tests_pass`）
  - 事件流断言（`trace_assert`：pytest 失败后最终修复过没有）
  - finish_reason 分布（error 率、max-tokens 率）
- **LLM-judge 补充**（只补确定性覆盖不了的维度）：成对比较（vs 基线）、rubric 细化、「长度不构成优势」、交换顺序跑两次（课程 06 章三大偏差对冲）

### 2.3 指标看板

| 维度 | 指标 | 数据来源 | 更新频率 |
|---|---|---|---|
| 质量 | 评估集通过率（分 tier）、finish_reason 分布 | 评估运行 | 每次改动 |
| 成本 | 每任务 token、每会话成本 | 事件流 usage | 每日 |
| 效率 | 步数分布、工具调用次数 | 事件流 | 每周 |
| 人类注意力 | 每任务人工介入次数/分钟数 | 你的审批/升级记录 | 每周 |
| Harness 健康度 | 工具错误率、循环信号、文档过期 | 事件流 + 你的规则库 | 每周 |

### 2.4 迭代记录表（纪律容器）

```
| 轮次 | 改动（一处） | 触发它的失败 | easy | edge | adversarial | 结论 |
|------|------------|--------------|------|------|-------------|------|
| 00   | 基线        | —            | 8/8  | 5/8  | 2/5         | 基线 |
| 01   | 工具 X 增加校验 | t07 误报   | 8/8  | 6/8  | 2/5         | 提升，保留 |
| 02   | persona 加规则 | t12 漏检   | 8/8  | 6/8  | 3/5         | 提升，保留 |
```

## 3. 怎么做：迭代闭环（每周一次，跑起来）

```
① 收集：从事件流/审计库拉本周失败的 trace
② 分析：按失败分类表归类（上下文/工具/验证/控制流——课程 04 章方法）
③ 修改：针对失败做 ONE 处改动（AGENTS.md/工具描述/约束/评估用例）
④ 验证：跑评估集（调参集看趋势）→ 人类复核 → 保留集发布前跑
⑤ 回流：新错误 → 错误日志 → 新评估用例（闭环永远不闭合）
```

**三条纪律**（课程 06 章原话）：
1. **只从失败出发**——成功案例不提供改进方向
2. **一次改一处，可归因**——改五处涨分了，你不知道是哪处的功劳
3. **人类验证不可省**——第 ④ 步也自动化 = 失去对抗过拟合的最后防线

## 4. 统计层（简洁版；完整理论见课程第 09 章）

- **别把噪声当信号**：n=20 时 ±22 个点的波动是常态。「这次 87% 上次 85%」大概率什么都没发生
- **bootstrap CI**（20 行代码，课程 09 章脚本直接抄）：指标带置信区间，区间不重叠才认真对待
- **保留集纪律**：调参集日常迭代，保留集发布时跑一次——「调参集满分 ≠ 真实改进」
- **A/B 五纪律**：同一评估集、同一跑法、随机顺序、盲评、只改一处

## 5. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 凭感觉迭代（「好像变好了」） | 无法归因、无法回归 | 评估集 + 迭代记录表是底线 |
| 评估集污染（任务进 AGENTS.md） | 开卷考试，分数失真 | 防污染三条纪律 |
| 一次改多处 | 涨分不知谁的功劳 | 一次一处 |
| 只看成功率 | 隐藏质量塌方 | 分层指标（reason 分布/工具错误/步数） |
| 无保留集 | 过拟合评估集（背答案） | ≥10 条保留集，发布时跑 |
| 错误日志断更 | 评估集断粮 | 从第一天建，每类新错误入账 |
| judge 不校准 | 另一种凭感觉 | 金标准集试运行一致率 ≥80% 再上岗 |
| 评估拖到上线前 | 迭代没有方向盘 | 第一周就建 10 条用例的评估集 |
