# 04 · 会话与记忆产品化：Agent 的「档案室」

> **核心问题**：会话是产品与用户交互的容器。会话策略（何时建、何时复用、如何隔离）与跨会话记忆（产品级知识怎么注入）决定了产品是「有记忆的服务」还是「每次失忆的对话」。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：接口细节 `../sdk-docs/02-快速上手-Python.md` §7（会话语义）；原理见课程第 02/05 章；dsh 会话机制见 `../deepseek-harness-解析.md` §2.1/§3.4。

---

## 1. dsh 给了什么（会话基础设施）

| 机制 | 作用 |
|---|---|
| **session 事件日志** | 唯一事实来源：对话、工具调用、注入上下文全部留痕 |
| **持久化**（JSONL/SQLite） | 会话落盘，跨进程/跨重启恢复 |
| **resume/fork** | 同名 session_id 恢复；fork 复制前缀（子任务继承轨道） |
| **compaction** | 长会话有损压缩（surface replace，可审计） |
| **spill** | 超大工具结果溢出到磁盘，上下文只留摘要+定位器 |
| **上下文预算** | token-meter 测量，40% 规则可落地（课程 02） |
| **多会话** | 一个 runtime 内多个独立会话（每 session 一个 agent） |

**关键认知**：dsh 把「档案室」建好了（日志+持久化+压缩）；你要设计的是**档案策略**——产品层面会话怎么组织、什么进长期记忆、租户怎么隔离。

## 2. 你要做什么：四个设计决策

### 决策 1：会话生命周期模型

| 阶段 | 你的决策 | 问题清单 |
|---|---|---|
| **创建** | 什么时候开新会话？ | 每个用户任务一个？每个用户一个？按主题？ |
| **复用** | 什么时候继续同一会话？ | 需要上下文延续时（修复任务、多轮讨论） |
| **归档** | 什么时候标记结束？ | 任务完成/超时/用户切换 |
| **清理** | 什么时候删？ | 保留期、存储成本、合规要求 |

**通用模式**：`session_id = 租户维度 + 任务维度`（如 `user-<id>-task-<n>`）。复用规则：**独立任务必新会话；延续性需求才复用**（官方教程原话："reuse an id only when the next call should continue the same durable conversation"）。

### 决策 2：多租户隔离

| 维度 | 隔离方式 | 推荐 |
|---|---|---|
| 会话数据 | `session_root` 分目录（`/data/sessions/<tenant>/`） | ✅ 必须 |
| 工作区 | `cwd` 分目录（`/workspaces/<tenant>/`） | ✅ 必须（danger-full-access 下尤其） |
| runtime 进程 | 每租户独立 harness 实例 | 安全敏感/合规场景 |
| 事件流 | 订阅端按 sessionId 过滤 | ✅ 必须 |

**铁律**：任何租户的 session 数据不能出现在另一个租户的会话里——`session_root`+`cwd` 分离是最低成本的正解；同实例多租户共享意味着工具执行在同一权限域，高风险场景上进程隔离。

### 决策 3：上下文预算管理

课程第 02 章的 40% 规则在产品里落地：

```
产品侧监控：
  - 会话事件流里统计 token（assistant/message.usage）
  - 接近预算 → 主动处理：总结归档 / 开新会话 / 触发 compaction
  - compaction 策略：挂 compaction 插件 + 调阈值（dsh 默认组合是关的，要显式开）
```

| 超限处置 | 适用 |
|---|---|
| 自动 compaction | 长对话延续（无损路径优先） |
| 会话续接（新 session + 注入摘要） | 超长任务、需要干净上下文（Context Reset 思想，课程 02） |
| 阶段重开 | 流程化任务的每阶段独立会话 |

### 决策 4：长期记忆注入（跨会话知识）

产品级记忆 = **你的数据库 → 显式注入**（dsh 的 session 日志只负责会话内记忆）：

```python
# 会话开始时的记忆注入（伪代码）
def build_initial_context(user_id: str, task: str) -> list[dict]:
    ctx = []
    prefs = get_user_preferences(user_id)          # 你的库
    if prefs:
        ctx.append({"type": "text", "text": f"用户偏好：{prefs}"})
    history = get_recent_conclusions(user_id, task)  # 你的库
    if history:
        ctx.append({"type": "text", "text": f"历史结论（供参考）：{history}"})
    return ctx

# 注入方式：首条 user/message（与任务同批）或 agent.inject（不进回合）
result = harness.run([*build_initial_context(uid, task), task_msg], session_id=sid)
```

**纪律**：注入的内容进 session 日志（dsh 保证可审计）；带时间戳与来源；定期复审（记忆会腐烂）。

## 3. 怎么做：会话策略模板

| 决策点 | 选项 | 我的选择 | 理由 |
|---|---|---|---|
| session_id 结构 | 用户+任务 / 仅任务 / 主题 | | |
| 复用规则 | 任务内复用 / 会话不跨任务 | | |
| session_root 组织 | 按租户 / 按产品 / 全局 | | |
| 归档策略 | 任务结束标记 / 超时归档 | | |
| 清理策略 | 保留 N 天 / 大小上限 | | |
| compaction | 开 / 关；阈值 | | |
| 长期记忆来源 | 哪些表、哪些字段、注入时机 | | |
| 审计需求 | 会话日志保留多久、谁可读 | | |

**填写这张表 = 完成会话产品化的 80%**。剩下的 20% 是接入（SDK 参数：`session_root`、`session_id`、注入逻辑）。

## 4. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| session 当垃圾桶（无限复用） | 上下文膨胀、40% 规则失效、成本飙升 | 任务级会话 + 归档规则 |
| 多租户共享 session_root | **数据串租户**（合规事故） | 租户分目录 + 订阅过滤 |
| 忘开 compaction | 长会话进入 Dumb Zone（课程 02） | 显式挂插件 + 阈值调优 |
| 注入无来源标记 | 审计说不清记忆从哪来 | 注入内容带来源+时间戳 |
| 记忆注入过载 | 挤占任务上下文 | 只注入「本任务需要」的（渐进式披露） |
| 会话数据永不清理 | 存储膨胀、合规风险 | 保留期策略 + 归档任务 |
| 跨进程恢复三要素不一致 | 会话「失忆」 | 同 session_root+cwd+session_id 才可恢复 |
