# 03 · 流程编排层：Agent 的「轨道」

> **核心问题**：任务怎么流？谁是轨道（确定性）、谁是节点（概率性）？这是产品与「通用 Agent」最大的区别所在。
> **四问框架**：dsh 给了什么 → 你要做什么 → 怎么做 → 常见坑。
> **交叉引用**：编排语言路线决策见前面对话结论与本篇 §4；原理见课程第 04 章；dsh 编排机制见 `../deepseek-harness-解析.md` §2.2/§3.3。

---

## 1. dsh 给了什么（编排基础设施）

| 机制 | 作用 |
|---|---|
| **agent-loop**（turn/step 驱动） | 单 Agent 循环：回合/步、流式、重试、取消——现成的 |
| **workflow 引擎** | 脚本化编排：`parallel()/pipeline()/agent()` 节点，worker 线程执行，防失控预算（并发上限/总节点上限/超时） |
| **subagent provider 注册表** | spawn/fork/acp/codex/claude-code…——可注册你自己的子代理后端 |
| **plan/goal/schedule/jobs** | 计划模式、同会话目标、定时触发、后台任务 |
| **turn 扩展点** | `agent/pre-step`（改每步输入）、`agent/turn-stopping`（回合停止前拦截）、`agent/request-error`（失败恢复）、`agent.steer/inject` |
| **preset** | per-session 能力组合（不同场景不同轨道） |

**关键认知**：dsh 把「执行引擎」做完了；你要做的是**流程设计**——任务分几步、每步做什么、谁验证、出问题怎么办。

## 2. 你要做什么：三形态流程决策

每个产品任务先回答：**它是哪种形态？**

| 形态 | 特征 | 谁驱动 | 典型产品 |
|---|---|---|---|
| **A 对话式开放** | 目标模糊、步骤不定、多轮交互 | 模型自由（L1+L2 就够） | 客服助手、Copilot |
| **B 分步任务** | 步骤固定/半固定，每步有明确产出 | **你的代码**（编排循环）或模型 | 审查流水线、数据处理 |
| **C 工作流引擎** | 步骤动态、并行 fan-out、需要管控 | 引擎（脚本） | 研究平台、多 Agent 协作 |

```
决策树：
任务进来 → 步骤能预先写死吗？
  能 → B：你的编排循环（Python/Node 都行）
  不能 → 分支可枚举吗？
    能 → B：分步 + 条件分支
    不能 → 需要并行 fan-out 或深度管控吗？
      能 → C：workflow 引擎脚本
      否 → A：对话式开放（模型自由）
```

**核心原则（课程第 04 章）**：能预定义路径就不要让模型自由发挥——确定性轨道 + 概率性节点的比例，就是产品的「工程化程度」。

## 3. 怎么做：分步任务设计模板（形态 B 为主）

每个任务按五段设计：

```
┌──────────────────────────────────────────────────────────┐
│ 任务：合同审查                                               │
│ ① 阶段划分（轨道）                                          │
│   提取 → 逐条规则检查 → 交叉核对 → 报告生成 → 人工复核        │
│ ② 每阶段输入/产出（上下文边界）                              │
│   提取：输入=合同文本；产出=结构化条款清单（不进下一阶段原始文本）│
│ ③ 每阶段验证点（Build-Verify）                              │
│   规则检查后：机械校验条款清单 schema + 必查规则覆盖率         │
│ ④ 人工介入点                                               │
│   高风险发现 → 审批；报告发布 → 人工确认                     │
│ ⑤ 失败恢复                                                │
│   每阶段重试 ≤2 次 → 降级（部分报告+标注）→ 升级人工           │
└──────────────────────────────────────────────────────────┘
```

**Python 编排循环的实现骨架**（形态 B 的主力，不写 TS）：

```python
class ReviewPipeline:
    STAGES = ["extract", "check", "cross-check", "report"]

    def run(self, task_id: str, contract: str):
        sid = f"review-{task_id}"
        for stage in self.STAGES:
            r = self.harness.run(self.prompt_for(stage), session_id=sid)
            if not self.verify(stage, r):        # 你的验证逻辑（确定性）
                if self.retries(stage) < 2:
                    continue                      # 带修复指令重试
                return self.degrade(stage, r)    # 降级/升级人工
        return self.finalize(sid)
```

## 4. 编排语言决策：Python 循环 vs workflow 脚本 vs Node 控制面

| 维度 | Python 编排循环 | workflow 引擎脚本 | Node 控制面（L3） |
|---|---|---|---|
| 轨道在哪 | 你的后端代码 | 脚本（模型或你写） | Node 服务 |
| 并行 fan-out | Python 线程+多 session 模拟 | **原生**（parallel/pipeline） | 原生 |
| 动态脚本 | 无 | ✅（模型可现场写） | 无（你写死） |
| 流程演进 | 改 Python 代码 | 改脚本 | 改 Node 代码 |
| 语言投入 | 零（你已有 Python） | 零～少量 | 几百行 Node |
| 适合 | 固定/半固定流程 | 动态、并行、模型自适应的流程 | 深度管控、多产品复用 |

**决策规则**：
- 流程固定或半固定 → **Python 编排循环**（最简单，轨道完全可控）
- 需要并行/动态 fan-out → workflow 引擎（模型驱动或代码驱动）
- 产品主流程就是 Agent 编排、需要引擎级管控 → Node 控制面（见前面对话的路线 2）

## 5. 人工介入点设计（产品可靠性的一半）

| 介入类型 | 触发条件 | dsh 机制 | 你的实现 |
|---|---|---|---|
| 审批 | 危险工具调用 | `PreToolDecision.ask` → approval | 产品内审批 UI/通知 |
| 转向 | 模型跑偏、用户想改方向 | `agent.steer()` | 产品交互（打断输入） |
| 升级 | 重试耗尽、低置信度 | 你的编排逻辑判定 | 人工队列 + 上下文打包 |
| 确认 | 对外交付前 | 你的流程设计 | 发布确认页 |

**原则**：人工介入不是失败标志，是可靠性设计。**接入点越早设计，产品越稳**——事后补审批 = 重新设计流程。

## 6. 常见坑

| 坑 | 后果 | 解法 |
|---|---|---|
| 过度编排（把简单对话搞成 8 步流水线） | 延迟、成本、脆弱 | 从最简单的形态开始，信号驱动升级 |
| 模型驱动 vs 代码驱动不分 | 流程不可控或开发过度 | §4 决策规则 |
| 阶段间上下文不隔离 | 原始文本/中间产物污染后续阶段 | 每阶段只注入本阶段需要的（课程 02） |
| 无验证点 | 错误在最后一步爆发 | 每阶段 Build-Verify（机械校验优先） |
| 无降级路径 | 失败 = 任务死亡 | 重试→降级→升级三连 |
| 多 Agent 滥用（任务大就上多 Agent） | 成本乘数、调试地狱 | 课程 04 章触发三条件先自查 |
| 人工介入点后补 | 流程返工 | 设计阶段就定介入矩阵 |
