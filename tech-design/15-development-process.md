# 15 · 任务驱动开发流程（Task-Driven Development）

> 状态：✅ 已确定
> 对应原则：原则零 Agent-First
> 配套文档：[10-agent-dev-environment](./10-agent-dev-environment.md)（验证闭环）、[12-development-standards](./12-development-standards.md)（规范）、[08-roadmap](./08-roadmap.md)（目标来源）
> 使用对象：开发 Agent、评审 Agent、人类维护者

---

## 0. 一句话

**从「目标」到「合入」的完整开发流程：目标明确 → 对齐 → 拆解 → 执行 → 验证 → 沉淀。** Agent 是执行者 + 规划者，人是产品负责人 + 最终审批者；对齐点少而准，其余全自动。

> 本流程回答 12 文档未覆盖的「规划层」：目标怎么明确、怎么与人对齐、怎么拆解。12 文档覆盖「执行层」：任务模板、提交、review、发布。

---

## 1. 流程总览

```
① 目标（Goal）     「做什么」   目标声明（一页纸）→ 对齐点 A 人确认 ✅
② 拆解（Plan）     「怎么做」   任务序列 + 任务工单 → 对齐点 B 人评审（大任务）✅
③ 执行（Do）       「做出来」   按任务工单实现 + 测试 + 自验证（小决策自主，大决策 ADR）
④ 验证（Verify）   「对不对」   CI 全量 + 评审 Agent + 人抽查 → 反馈闭环至全绿
⑤ 沉淀（Learn）    「留下什么」 合入 + ADR + 文档同步 + 规格追溯 → 进 knowledge
```

**角色分工**：
- **人** = 产品负责人 + 审批者：定目标、评审拆解、关键合入（只做这三件事）
- **Agent** = 执行者 + 规划者 + 质检员：起草目标、拆解任务、实现、自验证、修复

---

## 2. 阶段 ①：目标（Goal）

### 2.1 目标来源

| 来源 | 说明 |
|---|---|
| **roadmap**（08） | 阶段性目标，人的产品方向 |
| **Issue / 需求** | 功能请求、bug、用户反馈 |
| **探索任务** | spike、技术验证（如 file:// 验证） |
| **维护任务** | 依赖升级、重构、文档同步 |

### 2.2 目标声明（一页纸六问）

每个开发目标必须写成一页纸声明，回答六个问题：

```
# 目标声明：<标题>（引用需求 ID / issue）

1. 背景   为什么现在做？（数据 / 用户 / roadmap 依据）
2. 目标   完成什么？（可衡量，机器可验证）
3. 非目标 明确不做什么（防 scope 蔓延）
4. 受益者 给谁用？解决谁的什么问题
5. 验收   DoD 清单（可执行命令验证，不含「人工确认」）
6. 风险   可能失败的点与应对
```

**原则**：
- 非目标与目标同等重要——Agent 最容易 scope 蔓延（「顺手把 X 也做了」）
- 验收必须机器可验证（见 12 §1.2 DoD）
- 目标声明由 Agent 协助起草，**人确认**（对齐点 A）

### 2.3 对齐点 A：目标确认（必确认）

- 人确认目标声明后才进入拆解
- 确认内容：方向对、非目标合理、验收可执行
- 未确认的目标 = 不可开工（Agent 不得自行扩大目标）

---

## 3. 阶段 ②：拆解（Plan）

### 3.1 拆解原则

| 原则 | 说明 |
|---|---|
| **一个任务 = 一个可独立验证的增量** | 每个任务能过 CI、能测、能单独合入 |
| **依赖优先** | 先依赖后独立，形成可推进的任务序列 |
| **任务粒度 ≤ 1 workday** | 超时熔断（避免 Agent 卡死在一个大任务上） |
| **任务间可交接** | 每个任务有完整工单，换 Agent 不丢上下文 |

### 3.2 任务工单（Task Ticket）

```
任务 ID：TASK-<NNN>（关联目标声明 / 需求 ID）
目标：<一句话，引用目标声明的哪部分>
范围：<改哪些文件/模块>
依赖：<前置任务>
验收（DoD）：<可执行命令验证的清单>
预估：<工作量>
```

任务工单是拆解的最小单元，也是交接的载体（见 12 §6.3）。

### 3.3 对齐点 B：拆解评审（大任务必确认）

- **大目标**（跨模块、影响架构、>3 任务）：人评审拆解合理性（顺序、粒度、依赖）
- **小目标**（单模块、独立）：授权 Agent 自主，仅目标声明确认即可
- 评审通过后，Agent 按序执行

---

## 4. 阶段 ③：执行（Do）

### 4.1 自主边界

| 决策类型 | 谁拍板 | 说明 |
|---|---|---|
| 小决策（实现细节、命名、结构） | **Agent 自主** | 不打扰人 |
| 大决策（依赖引入、架构变更、契约破坏） | **写 ADR + 人确认** | 见 12 §6.4 |
| 需求不明确 | 读规格 → 仍不明则列待决策点 | 不假设 |

### 4.2 任务实现规范

- 每个任务：实现 + 测试 + 自验证（`npm run verify`）→ 提交（12 §3）
- 涉及视觉：附截图；涉及性能：附基准（12 §3.4）
- 失败处理：读结构化反馈 → 修复 → 再验；卡住则熔断上报（AGENT.md）

---

## 5. 阶段 ④：验证（Verify）

### 5.1 验证矩阵

复用 [10](./10-agent-dev-environment.md) §2 的完整验证矩阵（单元 / 视觉 / 三形态一致性 / 浏览器矩阵 / 安全 / 性能 / 契约）。任一不过即阻塞。

### 5.2 反馈闭环

```
提交 → CI（lint→test→visual→isomorphic→perf→contract）
     → 失败：结构化反馈回提交者（Agent 自动修复）
     → 全绿 → 评审 Agent → findings → 修复 → 零 blocker
     → 合入
```

---

## 6. 阶段 ⑤：合入与沉淀（Merge & Learn）

### 6.1 合入

- 合入门禁：CI 全绿 + review 零 blocker + 契约通过（12 §2.4）
- Squash merge，PR 描述成为 commit 主体

### 6.2 沉淀（Agent 开发的关键——防止重复发现）

| 沉淀物 | 内容 | 目的 |
|---|---|---|
| **ADR** | 关键决策（背景/选项/选择/后果） | 防换会话推翻重来 |
| **文档同步** | 规格/设计文档与实现一致 | 文档即真相 |
| **规格追溯** | 需求 ID → 测试 → 代码 链路更新 | 可追溯 |
| **踩坑记录** | 常见失败模式与解法 | 下个 Agent 不用重新踩 |

> 沉淀不是可选项——Agent 开发的长期质量依赖它。未沉淀的合入 = 知识丢失。

---

## 7. 对齐机制总表（A / B / C）

| 对齐点 | 时机 | 触发条件 | 人确认什么 |
|---|---|---|---|
| **A 目标确认** | 开工前 | 每次必确认 | 方向、非目标、验收 |
| **B 拆解评审** | 拆解后 | 大目标（跨模块/>3 任务） | 顺序、粒度、依赖 |
| **C 合入确认** | 合入前 | 关键/高风险（依赖、破坏性、视觉基线、发布） | 可合入性 |

**原则**：对齐点要**少而准**——多了失去自动化意义，少了 Agent 会跑偏。常规任务的 A + 自动验证即足够；B/C 按规则触发。

---

## 8. 人在流程中的角色

**人只做三件事**：
1. **定目标**（确认目标声明）
2. **评审拆解**（大任务）
3. **关键合入**（高风险合入确认）

其余（拆解细节、实现、测试、自验证、修复、文档同步、沉淀）全部由 Agent 自主完成。

**为什么这样**：Agent 自主开发的价值在于「无人值守闭环」。人的价值在方向与判断，不在执行——把人不擅长或不该做的（重复劳动）交给 Agent，把 Agent 不该做的（方向决策）留给人的精力用在刀刃上。
