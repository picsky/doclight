## 0. 一句话定位

**作品集（Collection）是 DocLight 的组织层：一个归属者（人 / Agent / 品牌）名下多个文档站的上层单元。**
站是主题内聚的（一个站 = 一个主题），作品集是归属聚合的（一个作品集 = 一个主人 + 若干互不相关的站）。
它回答「这些站都属于谁、都有哪些」，不渲染内容、不吞并站。

```
「我有一个产品文档站、一个课程站、一个个人博客、几份演示——它们主题毫不相干，
  但都是我的。DocLight 给我一个『作品集』把它们收拢，一张首页陈列全部。」
```

## 1. 背景与动机

### 1.1 时代判断：生产成本趋零，稀缺转向组织与信任

Agent 让内容生产效率急剧提高，信息再次爆炸——而且这次是**高质量信息**的爆炸。
生产不再是瓶颈，**信息的组织、管理与发布**成为新的瓶颈。

再进一步：当「看起来高质量」的内容唾手可得，稀缺的不只是组织，还有**信任与归属**——
「这是谁的全部产出、他持续维护着什么」本身就是质量信号。

由此推出两个方向：

1. **组织单元要完备**：文档 → 文件夹 → 站 →（缺失）归属层——本文档补上最后一层（§3）；
2. **每一层要有门面**：层内可导航、层间可发现——站要有一张首页，归属层也要有一张首页（§2）。

### 1.2 心路历程：一个「二选一」的伪问题

> 本节记录思考过程本身（防重走弯路）；结论见 §2。

信息单元已有三层：文档 → 文件夹 → 主题。一个主题对应一个站、一个独立 URL——
**但站还没有首页**。于是问题最初被摆成二选一：

- 给一个主题的站配单独的首页？
- 还是做一个首页聚合用户所有的主题？

中途的自我反驳：「既然做 site 这么容易，用户直接多做几个 site 不就好了？」——
但一个用户确实有把所有站聚合陈列的需求；同时，单主题的站配上自己的 home page 也是必要的。

**收敛：这不是二选一——两个首页在不同层、服务不同受众，各缺一块拼图（§2）。**
「站容易做」恰恰推出「多站是常态」：作品集不是替代多站，而是给多站补上「归属可见性」。

### 1.3 断点：站是主题内聚的，装不下「归属」

DocLight 目前只有一个组织单元——**文档站**（`docs/ + doclight.json`）。站的全部能力（导航 / 搜索 /
主题 / SEO / 域名）都为一个主题服务，这是站的优势，也是站的边界：**完全不相关的内容不该放进一个站**。

Agent 已是内容生产主力（01 §目标用户第一用户），一个 Agent / 一个用户的产出天然是多主题的：
产品文档、教程站、课程站、个人博客、演示……这些互不相干，却都属于同一个人。**缺一个「归属层」
把它们收拢**——这是本次设计的动机。

### 1.4 竞品规律：站的上层是「谁拥有」

| 产品 | 主题内聚单元 | 归属聚合单元 |
|---|---|---|
| GitHub | 仓库（repository） | 组织 / 账户 |
| GitBook | Space | Organization |
| 语雀 | 知识库 | 团队 |
| Notion | Page | Workspace |
| **DocLight** | **文档站** | **作品集（本次新增）** |

规律一致：**站是主题的，再往上一层是「谁拥有」的**。DocLight 目前只有前者。

补充信任视角：GitHub 的对应物不是某个功能，而是**个人 profile 页**——repo README 回答
「这个东西怎么用」，profile 回答「我该不该信这个人的产出」。两个问题、两批受众，互不替代。
**作品集（及其聚合首页）是 DocLight 的信任面，站点首页是消费入口——二者成对出现（§2）。**

### 1.5 与「空间」的关系（不冲突，正交）

DocLight 已有「空间」概念（`.doclight/space.json`，14 §3）——但那是**发布目标**（部署到哪：local / git /
cloud），不是组织单元。二者正交：

- **组织轴（本次新增）**：作品集 → 站 → 文件夹 → 文档（归谁、装哪些）
- **部署轴（已有）**：空间 = 发布目标（发到哪）

同一个作品集里的站可以发布到**不同**的空间（站 A → GitHub Pages，站 B → 本地 bundle），互不干扰。
代码与文档里两个词各归其位，`collection` 不碰 `space`。

## 2. 两个首页：不同层、不同受众，不是二选一

| | 站点首页（前置件） | 作品集首页（本文档主体） |
|---|---|---|
| 回答什么 | 这个主题是什么、从哪读起 | 这个人 / Agent 都产出过什么 |
| 服务谁 | 陌生读者（冲着主题来） | 认识「主人」的人、跨主题访客、主人自己 |
| 属于哪条轴 | 站自身的内容体验（站自己的缺件） | 归属层的陈列面（新层） |
| 类比 | repo 的 README / landing | GitHub 个人 profile |
| 更新频率 | 跟随内容 | 跟随「我又做了什么站」 |

### 2.1 依赖关系：站点首页是前置件

**作品集首页的每张卡片，落点都是站——而站今天没有首页。**卡片链过去，读者看到的是
第一篇文档、或什么都没有。作品集首页把「站没有首页」这个缺口，从「站自己的待办」
升级成「聚合体验的断点」。

- 站点首页必须**先行或同批**交付（§12：Phase 8 = 首页双件）；
- 站点首页目前不在任何 Phase 里——这是本轮思考暴露出的 roadmap 缺口，由本文档显式化。

### 2.2 价值闭环：跨主题导流是单站给不了的

建站成本低 → 多站是常态 → 作品集补上归属可见性。一个读了你产品文档的读者，
会顺着作品集摸到你的课程站和博客——这是「多做几个 site」本身得不到的价值。
再加上预留的总 llms.txt / 总 MCP（§8），Agent 名下的站有一次统一发现的入口——
这是差异化，v1 不排期、只留位置。

## 3. 概念模型

### 3.1 两条轴，四层单元

```
组织轴（新增）                       部署轴（已有，不动）
─────────────────────              ─────────────────────
作品集  Collection    ← 归属单元     空间 Space = 发布目标
  └ 文档站 Site       ← 主题内聚单元   ├ local（本地 bundle）
       └ 文件夹 Group  ← 站内分组       ├ git（GitHub Pages）
          └ 文档 Doc   ← 内容单元       └ space（云端，已排除）
```

| 层级 | 单元 | 绑定什么 | 承载什么 | 主题约束 |
|---|---|---|---|---|
| L4 | 作品集 Collection | 归属者（人 / Agent / 品牌） | 多个站 + 统一身份 + 聚合首页 | 无（容纳不相关正是其意义） |
| L3 | 文档站 Site | 一个主题 / 项目 / 一次交付 | 导航 / 搜索 / 主题 / SEO / 域名 / **站点首页（前置件）** | **必须主题内聚** |
| L2 | 文件夹 Group | 站内结构 | 层级、顺序、分组 | 站内主题 |
| L1 | 文档 Doc | 无 | 内容本身（正文 + frontmatter） | — |

### 3.2 单元的本质（是什么 / 不是什么）

| 是 | 不是 |
|---|---|
| ✅ 一个归属单元 = 目录 + 清单 + 聚合首页 | ❌ 不是渲染单元（不渲染 Markdown，站是唯一渲染主体） |
| ✅ 回答「这些站都属于谁、都有哪些」 | ❌ 不是吞并站（站保持独立原子单元，可脱离作品集单独存在） |
| ✅ 站的「陈列面」 | ❌ 不是统一主题 / 配置继承源（v1 不做下发） |
| ✅ 信任面：归属者的「全部产出」即质量信号 | ❌ 不是社交层（无关注 / 动态，见 §9 红线） |
| ✅ 延续「一个目录 = 一个东西」的 DNA | ❌ 不是团队协作 / 权限层（与「不做团队协作」定位冲突） |

## 4. 关键架构决策

### D1 — 作品集 = 「清单 + 聚合首页」，站仍是独立构建单元 ✅

- 站照旧 `doclight build` 独立产出三形态；作品集只多一个「聚合首页」产物。
- **否决「作品集整体渲染」**：会破坏三形态、体积门禁（ADR-0002）、SEO，且无必要——作品集不承载内容。
- **向后兼容零回归**：站是原子单元，现有用户（只有站、无作品集）完全不受影响。

### D2 — 聚合首页复用展示层设计令牌，但不走 Markdown 渲染管线 ✅

- 卡片墙是**产品 UI**，不是**用户内容**；塞进 markdown 违背「内容与表现分离」（01 §原则三）。
- 复用默认主题 CSS 令牌（宪法 DESIGN.md §3），保证与站视觉同源；DP-001 单主题收敛后，一致性零成本。
- 不新增渲染扩展、不引入新依赖。

### D3 — 单事实来源：站元数据只存在站的 `doclight.json` ✅

- `collection.json` 只存「站路径 + 排序 + 可选展示覆盖」，**不复制**站的 title/description。
- 聚合首页构建时读取各站 `doclight.json`（title/description/theme）+ `docs.json`（文档数/更新时间）。
- 避免「两处维护同一标题」的经典错误；覆盖字段仅用于「作品集语境下的展示名」，站自身的 doclight.json
  仍是权威。

### D4 — 与「空间」正交，命名不冲突 ✅

- `space` = 部署（发到哪），`collection` = 组织（归谁、装哪些），代码与文档各归其位。

### D5 — 三形态齐备 ✅

- 聚合首页同站一样支持 dev（预览）/ SSG（构建产物）/ bundle（单文件）三形态，与站同一哲学（02 §2.4）。
- bundle 聚合首页只内嵌「卡片数据」，点击站卡片跳转到站的产物（相对路径或部署 URL），**不内嵌站内容**。

### D6 — 物理包含：站是作品集的子目录 ✅

```
我的作品集/                      ← 作品集根（一个目录 = 一个作品集）
├── collection.json             ← 作品集清单（身份 + 站列表）
├── product-docs/               ← 站 A（独立 doclight.json + docs/）
│   ├── doclight.json
│   └── docs/
├── course-site/                ← 站 B
│   ├── doclight.json
│   └── docs/
└── dist-collection/            ← 聚合首页产物（collection build 产出）
```

- 延续「文件即真相、无锁入」：**拷贝作品集目录 = 迁移整个作品集**；可整体 git 管理（一个 repo = 一个作品集）。
- 否决「逻辑引用（任意路径）」：作品集不自包含、路径脆弱、无法整体迁移，违背无锁入。
- ⚠️ 已知坑：把「独立 repo 的站」收编进作品集会产生嵌套 repo / 原 CI 路径断裂问题（§11-6）。

### D7 — 卡片墙机制分形共享：一套机制，两层首页 🟡（倾向案，待定稿）

- 站点首页与作品集首页**共用同一套机制**：卡片墙 + 默认主题 CSS 令牌 + 不走 Markdown 渲染管线（延续 D2 先例）。
- **站点首页（提案）**：缺省自动生成「顶层文件夹 / 文档的卡片墙」；存在 `docs/index.md` 时由用户内容覆盖——
  约定优于配置、缺省可覆盖，延续 doclight.json 的 DNA。
- **作品集首页**：站的卡片墙（§6）。
- 分形结构：卡片墙机制写一次，两层受益；`docs/index.md` 覆盖是「产品 UI 让位于用户内容」的边界用例。
- 待定：站点首页形态定稿与需求 ID 归属（§11-1 / §11-2）。

## 5. 数据模型（`collection.json`）

### 5.1 契约草案

```json
{
  "name": "我的作品集",
  "description": "一个 Agent 的所有产出",
  "sites": [
    { "path": "product-docs" },
    { "path": "course-site", "order": 0, "description": "课程站（作品集语境下的展示描述）" }
  ]
}
```

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `name` | string | 否 | 作品集名；缺省取目录名 |
| `description` | string | 否 | 作品集一句话描述 |
| `sites` | array | 是 | 站清单（可空数组） |
| `sites[].path` | string | 是 | 站目录相对作品集根的路径 |
| `sites[].order` | number | 否 | 排序（缺省语义待定死：添加顺序 or 字母序 → §11-5） |
| `sites[].title` | string | 否 | **覆盖**站的标题（作品集语境展示名，缺省读站 doclight.json） |
| `sites[].description` | string | 否 | **覆盖**站的描述（缺省读站 doclight.json） |

### 5.2 设计原则

- 字段扁平、看名知义、Agent 好读写（延续 doclight.json 原则，02 §2.5）
- 全部字段有缺省，配置是「改默认」不是「必须写」
- `sites[].path` 之外全是可选覆盖；标题/描述默认从站读取（D3 单事实来源）
- 契约文件：`contracts/collection.schema.json`（**新增**文件，不改既有 doclight.schema.json，守「schema 只加不改」红线）

## 6. 聚合首页形态

### 6.1 卡片墙

每个站一张卡片，信息：

| 卡片字段 | 数据来源 |
|---|---|
| 标题 | 站 doclight.json.title（可被 collection.json 覆盖） |
| 描述 | 站 doclight.json.description（可覆盖） |
| 主题色 / 图标 | 站 doclight.json.theme / 可选 icon |
| 文档数 | 站产物 docs.json 的 totalDocs |
| 更新时间 | 站产物 docs.json 的最新 updatedAt |
| 链接 | 站产物路径（SSG）或部署 URL（**来源待定 → §11-4**；卡片落点是站点首页 → §2.1） |

### 6.2 视觉

- 复用默认主题 CSS 令牌（宪法 DESIGN.md §3：松绿 Pine 强调色、8pt 网格、发丝线、≤300ms 动效）。
- 聚合首页自身是**一张页面**，无侧边导航 / 搜索 / 多页渲染。
- 暗色模式跟随系统（与站一致）。

### 6.3 三形态

| 形态 | 命令 / 产物 | 说明 |
|---|---|---|
| dev 预览 | `doclight collection build --dev` 或 dev 服务器挂载 | 本地预览卡片墙 |
| SSG 构建 | `doclight collection build` → `dist-collection/` | 静态产物 + 链接各站产物 |
| bundle 单文件 | `doclight collection bundle`（可选） | 内嵌卡片数据，站卡片外链 |

> bundle 聚合首页为可选增强（v1 可后置）：其价值低于站 bundle（站 bundle 是「离线看内容」，
> 作品集 bundle 只是「离线看目录」，外链仍需站产物或部署 URL）。

## 7. CLI 命令族

与 `space` 对仗（一个管组织、一个管发布），Agent 一看就懂：

```
doclight collection init [name]        # 在当前目录初始化作品集（生成 collection.json）
doclight collection add <name>         # 在作品集内新建一个站（子目录 + doclight.json + docs/）
doclight collection add --path <dir>   # 把现有站搬入作品集（移动到子目录 + 登记）
doclight collection list --json        # 列出作品集内的站（结构化，Agent 可读）
doclight collection build              # 构建聚合首页（三形态）
```

- 所有命令输出结构化 JSON（`--json`，Agent 直接消费，延续 CLI-005/006 原则）
- `add --path <dir>` 处理「已有独立站收编进作品集」的迁移场景（移动目录 + 登记，无格式转换）；
  收编独立 repo 站的副作用待处理（§11-6）

## 8. AI 接口（预留，v1 不做）

作品集级的「总 llms.txt / 总 MCP」——Agent 一次发现名下全部站——是 DocLight 的天然差异化
（延续 14 §1.1「Agent 生产的内容没有家」，作品集就是那个「家」的门牌；也是 §2.2 价值闭环的远期形态）。

按用户决策（v1 只要聚合首页），**不排期**，仅在 `collection.json` 预留 `ai` 字段位置（不实现、不进 schema）。

## 9. 范围与边界（YAGNI 红线）

### 做（v1 作品集 + 前置件）

- `collection.json` 契约 + `contracts/collection.schema.json`
- `doclight collection init / add / list / build` CLI 命令族
- 聚合首页（卡片墙）dev / SSG 双形态（bundle 可选后置）
- 站元数据聚合读取（D3 单事实来源）
- 物理包含目录结构（D6）
- **站点首页（前置件）**：缺省卡片墙 + `docs/index.md` 覆盖（形态随 D7 定稿，需求 ID 待登记 → §11-2）

### 不做（明确排除，防蔓延）

| 排除项 | 理由 |
|---|---|
| 作品集内站的**分组 / 标签 / 站内搜索** | 过度设计；v1 平铺即可 |
| **跨站全文搜索** | 大工程，非首需 |
| **统一配置 / 主题继承下发** | 站各自为政更符合无锁入 |
| 作品集级**总 llms.txt / 总 MCP** | 预留，v1 不做（§8） |
| **云端作品集托管** | Cloud Space 已排除（用户决策） |
| **权限 / 团队协作** | 与「不做团队协作」定位冲突 |
| **平台化（关注 / 动态 / 订阅 / 社交关系）** | 归属层是**静态陈列**不是社交层；一旦平台化即从工具滑向内容平台，偏离定位（红线） |

## 10. 需求拆分与 ID

新前缀 `COLL`（作品集 Collection，4 字母，符合 ID 正则 2-5 大写字母）——已登记 `specs/README.md` 前缀表。
